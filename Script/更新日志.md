## 0.26.9 菜单UI

- 加了个右键菜单

### 统一 · "开启 UI"只剩一个入口
- **`UiSystem.open_ui(preset_name, host := null, anchor := null)`** —— 全项目唯一开启入口，普通 UI 与菜单走同一条路：
  - `host` 为空 = 独立 UI（挂 UI 根，登记名就是预设名，如 `MiniHUD`）；给了 = 寄主型（菜单/提示，挂到宿主下，登记名 `宿主名/预设名`）。
  - 已存在就**只显示 + 重新摆位**，不重建控件：独立 UI 按预设名在 `uis` 里找，寄主型按"同一宿主 + 同一预设"找 `UI_Menu.find_instance`。
  - 摆哪由被开启 UI 自己的 `config["open_at"]` 决定，新增 `Enums.OpenAt.CONFIG`（不写 `open_at` 时的默认：摆回 `config["position"]`）；摆放策略从 `UIInteract` 收进 `UiSystem._place`。
  - `UIInteract.open_ui(target, preset_name, anchor)` 只剩**转发**（指令里的 `$self`/`$parent.parent` 要先由 `resolve_cmd` 解析成实例，所以保留这个壳，它不含任何策略）。
- `Test.ui_test` 不再直接调内部函数，改成与游戏内一致的**发指令**：`Msg.send_cmd("UIInteract.open_ui --preset_name MiniHUD")`——测试 UI 与游戏内 UI 从此同一条开启路径（想手动开关就把这条指令绑到快捷键上）。顺手删掉没用的 `Test._dump_ui`。
- **删除无调用者的代码**：`UiSystem.add_ui`（被 `open_ui` 取代）、`UiSystem.add_element`、`UiSystem.remove_ui` + `_collect_tree`（关闭就是 hide，没人销毁）、`UiSystem.check_ui`、`UIBase.remove_child_element`、`UIInteract.open`（它只是"原地 show"，等于第二种打开方式）。
  - 连带说明：`Msg.send_ui_remove` 目前**没有任何发送方**（已无销毁路径），保留给以后真要销毁时用——那时记得同时接上 `listen_ui_remove` 的接收方。

### 修复 · 菜单一打开就消失 / 关掉后再也开不出来（高度 0 的退化矩形）
用探针实测拿到结论（打印根控件尺寸），**与"隐藏后再显示"本身无关**——`hide()` / `show()` 实测完全对称：

```
[menu.build]  size=(150.0, 0.0)   global_rect=[P:(0,0), S:(150,0)]   ← 高度 0
[panel.build] size=(320.0, 220.0)                                    ← 正常
```

- 原因：`UI_Panel` 的根是**普通 `Control`，不会汇总子元素的最小尺寸**，`_fit_size()` 里 `control.get_combined_minimum_size()` 拿到的只是 `custom_minimum_size`——菜单配置 `"size": [150, 0]`（宽固定、高随内容）就被补成**高度 0 的退化矩形**。而 `PointerDetect._ui_at` 用 `get_global_rect().has_point()` 判命中，高度 0 永远命不中它自己（指针正好落在它的边距里），于是**同一个按键事件里紧接着的失焦检查**判定"指针在菜单外" → `close_self` → **同一帧内刚 show 就被 hide，屏幕上根本看不到**；位置却是对的，因为 `show_at` 是先摆位再显示。
- 修法（只动 UI 自身的尺寸来源，不碰可见性、不碰父子关系）：
  - `UIBase` 新增 `_content_size()`（默认 `control.get_combined_minimum_size()`），`_fit_size()` 改用它——"内容需要多大"从此是可覆写的点，容器类各报各的。
  - `UI_Panel` 覆写为 `_panel.get_combined_minimum_size()`（真正的容器，带边距 + 内容），并挂在 `_panel.minimum_size_changed` 上重算：建时还没进树、字体/主题都问不出来，只在 `build()` 末尾补一次会停在 0。
  - 实测复验：`[menu] size=(150.0, 62.0)`，`hide()` → `show()` 前后都正常。
- 纠正：上一版以为 `_fit_size()` 已经修好了退化矩形，其实对 `UI_Panel` 从未生效（它问错了对象）。也再次确认这与"父子可见性""实例复用"无关。

### 修复 · UI 关闭后无法重新打开（开启分支对已有实例什么都不做）
- 旧 `add_ui` 在 `uis.has(name)` 时直接 `return NOT_MODIFIED`，而 `close` 只是 `hide()`、实例仍留在 `uis` 里 → "开启"这条路对一个隐藏的 UI **什么都没做**。已随上面的"唯一入口"一并改成"没有就建、已有就显示 + 摆回配置位置"。
- `UIBase.reset_position()`（按 `config["position"]` 摆回初值）是这次抽出来的，"建时"与"重新开启已有 UI"共用同一份摆位逻辑。
- **同类陷阱**（已写进 `Script/UI/UI.md`）：`PointerDetect._ui_at` 用 `is_visible_in_tree()` 判命中，**隐藏的 UI 再也收不到任何事件**——所以"重开"的触发不能写在被关掉的那个 UI 自己身上（"再点它一下"是点不到的），必须来自它仍可见的父级、或系统级的状态/快捷指令。菜单项的"关闭"关的是宿主（设计如此：菜单只是快捷方式），宿主一隐藏，右键就再也派发不到它。

### 注释规范 · 全项目函数/属性都补上"作用 + 被谁所用"
- 目的：**改一个函数之前，先看它的注释就知道该同步哪些引用点**（配合"同需求同策略：一个需求只留一个实现入口"的约定）。
- 格式：函数/属性上方两行——第一行写"它是什么、为什么这样设计"，第二行统一写 `## 被谁用：...`（列出引用它的函数/文件）。
- 覆盖范围：`Script/` 下全部 54 个 `.gd`。
- 大文件采取"段落级 + 机制级"注释，避免噪音：
  - `MessageHub.gd`：文件头写三条约定（本类只管 ID 规则、收发在 `MsgBus`；段的 ID 规则收在段顶 `_format_*`；成串的 `send_*/listen_*` 是同模板薄包装，**查谁在用直接 grep 函数名**）+ 每个域（时间/输入/指令/属性/buff/状态/交互/碰撞/背包/技能/快捷/UI）段首写 ID 规则与主要收发方。
  - `CommandParser.gd`：补两级缓存（L1 LRU + L2 时间桶）与 `$` 表达式"编译成计划 → 运行时只取值"的设计说明。
  - `StatusPreset.gd` / `Attributes.gd` / `MapLayer.gd` / `TileSetPreset.gd` / `TileSpritePreset.gd`：逐函数标注用途与调用方。

### 规范 · 更新日志前先复查被改代码
- 流程固定为：改完代码 → **复查本次改动涉及的函数/属性的"作用 / 被谁用"注释是否还成立**、有没有新的引用者被漏掉、有没有指向已删除成员的说法 → 修正注释与文档 → 最后才写日志。这样日志里的"改了什么、影响谁"是核对过的，不是凭记忆。
- 本次复查发现并修正 3 处陈旧引用：
  - `Script/UI/UI.md` 指令表里仍有 `UIInteract.open $parent`（该指令已随"开启入口唯一化"删除）→ 换成 `UIInteract.open_ui [宿主] 预设名 [锚点]`（宿主省略 = 独立 UI）。
  - `UIPreset.gd` 的 `ui`："被谁用"还写着 `Test.ui_test`（测试已改成发指令）→ 改为只列 `UiSystem._build_open`，并补一句"它是共享模板实例，寄主型走 create_element + 深拷贝配置，别往它上面存实例态"。
  - `MessageHub.gd` 的 UI 段落补注：`send_ui_remove` 当前没有发送方（见上）。
- 复核结论：本次统一改动涉及的其它成员（`UiSystem.open_ui` / `_find_open` / `_place`、`UIBase.reset_position` / `show_at` / `_fit_size` / `_content_size`、`UI_Menu.find_instance` / `close_self` / `has_any_open` / `notify_key_event`、`Enums.OpenAt`）的"被谁用"与实际引用一致，无需改动。
